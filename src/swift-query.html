Swift Query, a Library for Asynchronous State Management

These past few months, I’ve been working on standardizing a set of tools that I’ve been using across a few of my Swift projects. Today, I’m opening them up to you to use in your applications, and I believe these tools will largely remove headaches around data consistency from remote/asynchronous data for you. This article will largely be about my inspirations for building such a library, and what I think it means for how we manage application state derived from asynchronous data in Swift.

You can check out the library here for a more direct dive into its features, and the many demos, case studies, and documentation articles I’ve prepared. I believe that this library is quite flexible, and can be used in a variety of ways that I don’t even know of yet. I wanted to document as many of the strategies that I’ve used it in real projects in its documentation, and I believe you will also be able to find ones that I haven’t figured out myself. If you find some cool use cases that I haven’t documented, let me know such that we can either get a case study or an article going.

As a whole, I want to keep this article related to the higher-level problems that are being solved by the library. Checkout the repo if you want a typical overview of its features with plenty of examples.


Background and Inspirations

The past 1.5 years using React Native at a startup is largely responsible for my inspirations for building Swift Query. In particular, the networking/asynchronous data needs of many sizeable applications are massive in this day and age, and I had the pleasure of having to combine networked data from multiple different sources and local databases stored on device. All of this data comes asynchronously, and takes a non-trivial but varying amounts of time to load from its source. As such, fetching asynchronous data itself through code isn’t typically the hard part, in fact it’s often done in just a few lines of code.

Yet, what does it mean to load asynchronous data? Such data comes from the physical world, because something physical must work to provide it, otherwise it we wouldn’t consider it “asynchronous”. As software developers, we rarely ever have to think of design in the context of the physical world. Rather, we love to create our own abstract worlds, and demand physical reality bends to our world. As such, we loathe error handling, keeping asynchronous data consistent when displayed in the UI, and creating systems with the expectation of failure.

Yet, if we want to build great experiences for our users, we need to collaborate with physical reality, and augment their ability beyond physical reality in our abstract worlds.

This all sounds incredibly philosophical, but it is exactly the reason why tanstack query is popular in the JavaScript world. The meaning of asynchronous data is incredibly complex in any given system, and if we’re to collaborate with physical reality we must design for failure. As such, we must implement retry mechanisms, caching, informative loading/error UI states, cancellation, keeping data consistent between screens, automatic refetching, stale-while-revalidate, network connection monitoring, exponential/fibonacci/linear backoff strategies, pagination, deduplication, and logging on top of our already existing application features. Tanstack query has an answer for all of this in the JavaScript world.

I get it, you have better things to be doing rather than implementing all of those mechanisms to collaborate with physical reality in Swift. Your users also think the same for the record. Therefore, I have decided to build a port of Tanstack Query that’s tuned for Swift, SwiftUI, swift-sharing, Concurrency, UIKit, Linux, WASM, and much more in the future. I want this library to aid the development of Swift as a true cross-platform language by solving such a common problem at the most literal level possible.

I built this library because I missed Tanstack Query when working in Swift.


Addressing Tanstack Query’s Limitations in Swift Query

Additionally, I aim to address many long-standing issues that Tanstack Query has in order to make something that can fit in to any of your asynchronous data needs. In other words, this library is meant to provide you a framework of thinking about asynchronous data by providing far more generic abstractions than Tanstack Query. This in turn may increase the overall learning curve of the library, but such a fate is better than it not being able to serve your needs.

Automatic Refetching

Tanstack Query will automatically refetch data when the user foregrounds your app, or the moment user’s network connection status flips from offline to online. Swift Query also provides these tools, but it also allows you to create your own custom refetch triggers by using the FetchCondition protocol. Therefore, you could make it so that data is automatically refetched when a user logs in/out, or when low-power mode is enabled, and much more.

Data Fetching Methods

Tanstack Query has 3 methods of fetching data suited for different purposes:

  • Queries
    • Fetching data as a single entire entity (this is the most common method).
  • Mutations
    • Mutating asynchronous data. (eg. HTTP POST request)
  • Infinite Queries
    • For paginating data (eg. Infinite scrolling lists).

Swift Query provides these 3 methods out of the box, but also allows you to create your own methods via the QueryRequest protocol. For instance, you could create a method that specializes in fetching recursive data, or combining multiple paginated data streams together.

Another difference from Tanstack Query is that in Swift Query, infinite queries and mutations are derived from typical queries. That is, MutationRequest and InfiniteQueryRequest are conformances to QueryRequest. In Tanstack Query, mutations are a completely separate concept not derived from queries, and there’s even a special MutationCache for caching their state. Such a cache is not needed in Swift Query, because mutations are queries. Additionally, deriving both infinite queries and mutations from typical queries allows QueryModifier conformances to work with all 3 methods by default.

Swift Query also differs slightly in how infinite query refetching works. In Tanstack Query, refetching an infinite query would refetch every single page starting from the beginning in a waterfall style. In Swift Query, only the initial page is refetched, and all other pages are simply removed. If you want to retain the Tanstack Query behavior, calling refetchAllPages on a QueryStore will do exactly that.

As for mutations, Swift Query adds 1 additional feature not found in Tanstack Query. In Tanstack Query, multiple calls to mutation.mutate will run concurrently, however the mutation state from useMutation only displays updates from the most recent call. Swift Query also works this way, but an additional history property exists that allows you to inspect the previous results from other calls to mutate.

Query Cache

Tanstack Query holds all of your query data in something called the QueryCache. This cache will evict entries based on a running timer in order to properly manage memory. Swift Query also implements uses a similar cache, but it evicts entries based on memory pressure warnings from the operating system instead of by a timer. However, the good news is that you can write your own custom query cache in Swift Query by conforming to the QueryClient.StoreCache protocol. Therefore, if you want the timer approach, you have the option to implement it yourself.

Query Client

The QueryClient in Tanstack Query holds all of your queries, and allows you to operate on them (eg. Refetching, invalidation, etc.). This is also the case for Swift Query, except that you aren’t required to attach a query to the QueryClient. You can use QueryStore.detached instead of obtaining a QueryStore through a QueryClient, and this will give you a store that runs its query in isolation. By doing this, you can even create your own state management system if you find that QueryClient does not suit your needs.

Additionally, the way one interacts with QueryClient in Tanstack Query is by calling methods such as refetch or invalidate directly on the client. Swift Query does not provide those methods on QueryClient. Instead, it provides methods that return QueryStore instances directly, and QueryStore has the appropriate refetch and invalidation methods. This allows you to perform advanced and composable operations on the QueryClient without you having to pester me to add a new method on QueryClient.

For example, the following (which is real-world code) can be done in 1 operation. Here, we’re removing queries from the client that correspond to files being deleted from a directory. Then, we’re refetching all queries that have a corresponding file that has had its data updated, and that are actively being displayed in the visible UI somewhere. 


extension QueryClient {
  public func processDirectoryChanges(
    _ changes: IdentifiedArrayOf
  ) async throws {
    let storesToRefetch = self.withStores(
      matching: .audioProperties,
      of: HapticaAudioProperties.Query.State.self
    ) { entries in
      let filesToRemove = changes.filter { $0.kind == .deleted }
        .map { HapticaAudioFile(id: $0.id) }
      for file in filesToRemove {
        entries.removeValue(forPath: .audioProperties(for: file))
      }
      return changes.filter { $0.kind == .dataUpdated }
        .compactMap { entries[.audioProperties(for: HapticaAudioFile(id: $0.id))] }
        .filter { $0.subscriberCount > 0 }
    }
    await withThrowingTaskGroup(of: Void.self) { group in
      for store in storesToRefetch {
        group.addTask { try await store.fetch() }
      }
    }
  }
}

You have access to all the necessary properties and methods directly on QueryStore to perform whatever state management you need. The withStores method takes a closure that allows you to edit the existing stores inside the QueryClient like you would a dictionary.

Query Keys

Swift Query’s QueryClient also supports pattern matching using a query key like in Tanstack Query. However, the query key is called a QueryPath in Swift Query, and QueryPath is a dedicated struct that can be constructed with an array literal of Hashable and Sendable elements.

Unlike Tanstack Query, your query is not required to specify a QueryPath if it conforms to Hashable or Identifiable. In such a case, the QueryRequest synthesizes a conformance for you. To visualize: 


struct MyQuery: QueryRequest, Hashable {
  // Does not need a query path...
}

struct MyQuery2: QueryRequest {
  // You must provide a query path because it is not Hashable or Identifiable...
  var path: QueryPath {
    ["my-query-2"]
  }
}

As an internal implementation note, a query key in Tanstack Query is represented by the full bloat of a JavaScript array. In Swift Query, the QueryPath type is optimized to not allocate an array when the path is either empty or only contains a single element.

By using a dedicated type for the paths, you can also create dedicated domain-specific constants by extending QueryPath. 


extension QueryPath {
  static let currentUser = Self("current-user")

  static func currentUserProject(for projectId: Int) -> Self {
    .currentUser.appending(projectId)
  }
}

Query Options

In Tanstack Query, you customize the behavior of a query by passing a bag of options, which looks like such: 


const myQuery = useQuery({
  queryKey: ["my-query"],
  queryFn: async () => {
    // Fetch the data...
  },
  retry: 3,
  staleTime: 5000
})

The problem with this approach is that the structure of the object is solely determined by the maintainers of Tanstack Query. You are essentially stuck with whatever configuration is deemed necessary by the library. There are ways around this, but generally they are not the most intuitive.

Instead, Swift Query defines queries as types, which allows for a modifier system similar to SwiftUI. In fact, you can create your own custom modifiers through the QueryModifier protocol. The disadvantage of this however is that queries require a some additional boilerplate due to needing to create an entire separate type for each one.

Here’s the same query written in swift query.


struct MyQuery: QueryRequest {
  var path: QueryPath { QueryPath("my-query") }

  func fetch(
    in context: QueryContext,
    with continuation: QueryContinuation<Value>
  ) async throws -> Value {
    // Fetch the data...
  }
}

let myQuery = MyQuery().retry(limit: 3).stale(after: 5)

Having a custom modifier system means that you can configure your queries in ways that the library doesn’t natively support, and work such support into your own app. For instance, the library doesn’t ship with a native method to artificial delay a query, but such a modifier can easily be written and used across many different queries. 


struct DelayModifier<Query: QueryRequest>: QueryModifier {
  let delay: Duration

  func fetch(
    in context: QueryContext,
    using query: Query,
    with continuation: QueryContinuation<Query.Value>
  ) async throws -> Query.Value {
    try await Task.sleep(for: self.delay)
    return try await query.fetch(in: context, with: continuation)
  }
}

extension QueryRequest {
  func delay(for duration: Duration) -> ModifiedQuery<Self, DelayModifier<Self>> {
    self.modifier(DelayModifier(delay: duration))
  }
}

let myQuery = MyQuery().delay(for: .seconds(0.3))

Multiple Data Updates

Tanstack Query provides a streamedQuery utility to allow you to yield multiple updates from your queries. This function requires that your query returns a JavaScript AsyncIterable, and the library handles the rest. Instead, Swift Query allows you to yield multiple updates from your queries via the QueryContinuation handed to your query.

This makes it easy to implement patterns such as.


struct SomeQuery: QueryRequest, Hashable {
  func fetch(
    in context: QueryContext,
    with continuation: QueryContinuation<Value>
  ) async throws -> Value {
    let localValue = try await LocalDatabase.fetchValue()
    continuation.yield(localValue)
    return try await Server.fetchValue()
  }
}

Ultimately, you’re still forced to return a final value from your query. If that value is no different from the last yielded value, then simply return the last yielded value.


Integrating with your App Architecture

One of my core principles with this library was to not care about your architecture as much as possible. That is, whether or not you use MVVM, TCA, MV, or some other combination of MXX, the library should still work for your use case. From my usage so far, I’ve had no trouble using the library in each of those architectural patterns. I also have taken making the act of writing tests heavily into consideration, and all the demos and case studies in the repo have sufficient test coverage to demonstrate this.

Concurrency

The library is also on the bleeding edge of Swift Concurrency, and provides tools that let you run your queries on custom TaskExecutor conformances and more. Everything is appropriately Sendable, and you can use the library from any actor or thread in your app. The only limitations are that the data types you return from your queries must also be Sendable, your query structs themselves must also be Sendable, and to make sure that you hop to the main thread if you’re observing QueryStore directly for UI updates.

The library also runs its work via the QueryTask type. This is a special wrapper around a typical Swift Task that doesn’t begin scheduling its work immediately after initialization. Rather, you tell it explicitly when to run via runIfNeeded, and you can also use it to schedule work in a serial manner compared to other tasks via calling task1.schedule(after: task2). If you end up scheduling tasks in a cycle, the library will warn you about this. In particular, you’ll find the flexibility of this type to be very useful for testing, as it gives you control over when your query is executed.

Network Layers

Another principle of the library is abtstracting over an async function in general, and not over the network.

You may find that you want to write all of your networking code directly inline inside your query structs, like so. 


struct UserQuery: QueryRequest, Hashable {
  let id: Int

  func fetch(
    in context: QueryContext,
    with continuation: QueryContinuation<User>
  ) async throws -> User {
    let url = URL(string: "https://api.myapp.com/user/\(self.id)")!
    let (data, _) = try await URLSession.shared.data(from: url)
    return try JSONDecoder().decode(User.self, from: data)
  }
}

Certainly, you can do this, and it is definitely fine for smaller apps. However, Swift Query was designed to enhance your network layer, and not replace it. In fact, you’ll find that in all of the demos and case studies that the query structs themselves are actually quite small, and that they usually call out to a method (on some API class) that actually performs the real data fetching.

Regardless, the library’s choice to abstract over a plain async function allows you to implement your queries no matter how well defined your app’s network layer is.

Future Directions

In general, I think the library provides all of the essentials today, but there are a few things that I want to look into in the potential future.

  1. Better defaults on Linux.
    • As of now, the library will compile and run on Linux, but there is no default NetworkObserver or ApplicationActivityObserver provided by the library. As such, you’ll be forced to create your own conformances if you want your queries to automatically be refetched when the your app foregrounds, or when the user’s network connection flips from offline to online.
  2. A better default store cache on non-Apple platforms.
    • Currently, the default store cache listens for memory pressure warnings from the operating system via DispatchSource.makeMemoryPressureSource. This API, or really it seems any memory pressure API, is not available on non-Apple platforms. As of now, the default store cache on non-Apple platforms will not automatically cleanup unused queries in any way. Of course, you can implement your own store cache to get around this, but a better default would be ideal here.
  3. Typed QueryContext.
    • Right now the QueryContext is untyped and has no generics. As such, context properties often have to be stored as any Sendable or any MyProtocol, and then casted to the appropriate strong types in the right contexts. I would like to see if it’s possible to add some sort of strong typing to this in the future.
  4. An official headless mode.
    • In some cases, you may want to run a query in some background process (eg. In a Tool in the new Foundation Models framework) instead of in the UI. This way, you can still benefit from modifiers such as retries, exponential backoff, duration logging, and much more. However, doing so would require constructing a QueryStore, which is explicitly meant for managing the query’s active running state in your application. In a background context, this additional state management is largely unnecessary because you’re not rendering any UI.

Start Using Swift Query Today

You can start using Swift Query today in your apps. However, I have not yet declared that the library is fully stable, so proceed at your own risks. In any case, try it out and let me know how it goes.
